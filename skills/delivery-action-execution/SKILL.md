# 动作执行阶段

任务面板四个技能里的第三个（拆解 → 梳理需求 → **动作执行** → 成品测试），负责单条任务的 `phase=development` 回合：按提示词给出的需求真正实现并自验，把本轮设计过程写进任务设计文档目录，最终回复作为「动作执行产物」保存到任务上。

## 会话前提

- 这一轮由任务面板的执行桥发起，任务已经被领取并绑定到当前会话；桥接器按本回合的最终状态自动同步面板。
- 不要执行 `create-task-board-*` 动作创建任务；发现缺口写进最终回复的「后续建议」。
- 阶段推进（动作执行 → 成品测试）由用户在面板上操作，本轮不要顺手把测试报告写了。

## 1. 取需求

哪几份文档存在、按什么顺序读，提示词已经在应用层核对好并写死了，**不要自己再判断、也不要去试探性地读不存在的文件**。剩下要你判断的只有两件事：

- **怎么读**：需求级文档和任务级 `文档.md` 都按标题定位到本任务真正涉及的章节，不要为了通读整篇载入——它们动辄一两万字，整份读进来的代价见第 2 节。
- **和代码对不上怎么办**：小的出入按代码事实实现并在回复里记录；方向性冲突停下来说清楚，不要自作主张改需求。

## 2. 上下文纪律

一轮动作执行里模型会被请求几十次——**每一次工具往返都要把当前全部上下文重发一遍**。所以一份 20k token 的读取结果不是只花 20k：它会在此后的每一次请求里再被计费一次。实测一轮烧掉 600 万输入 token，其中绝大部分是被反复重发的文件正文。按下面几条控制，这是本技能里优先级最高的约束：

- **同一个文件不要读第二遍。** 已经读进上下文的内容一直都在，要回看就往上翻。实测出现过同一个 4000 行组件在一轮里被读 16 次、同一份 4600 行 CSS 被读 5 次——这一条就是冲它来的。
- **超过 800 行的文件一律先定位再窄读。** 先 `grep -n` 拿行号，再用 `offset`/`limit`（或 `sed -n '起,止p'`）只读那一段。要看结构就 `grep -n` 抓骨架（导出、函数名、章节标题），不要为了"先看看长什么样"整份读进来。
- **要改的地方也只读要改的那一段。** 编辑需要精确原文，但需要的是那十几行，不是整份文件。
- **改动本身也占上下文。** Edit 的 old_string/new_string、Write 的整份内容，写出去之后同样永久留在会话里，此后每一次请求都跟着重发。实测一轮里 17 次 Edit 共 1.7 万字符、1 次 Write 1.1 万字符，合计占了对话正文的 24%。所以：定位用能唯一命中的最短片段，不要把整段函数或整个 JSX 块贴进 old_string；一处大范围改动宁可拆成几次小 Edit，也不要整段贴进去重写。
- **命令输出必须收口。** 任何可能刷屏的命令都接管道：`2>&1 | tail -40`、`| head -50`、只要数量就 `grep -c`。构建、类型检查、测试的完整输出一旦进上下文，之后每一次请求都在为它付钱。
- **能合并的往返就合并。** 相互独立的 `grep` / `wc` / `find` / `ls` 用 `;` 串成一条 Bash 命令一次拿回；少一次往返就少一次全量上下文重发。同一个目录下的多条命令用 `cd 目标目录 && cmd1; cmd2` 一次跑完，或者干脆用绝对路径——实测一轮 30 条命令里，大半是反复 `cd` 到同一个目录的碎调用。
- **项目技能的 `references/` 按需下钻。** 先读技能主文件 SKILL.md；`references/` 下的长文只在真的要动它覆盖的那类改动（新增模块、跨层调用、拆服务、新建页面、改设计系统）时才打开，且只读相关章节。常规改动靠 SKILL.md 里的速查内容就够。

## 3. 按项目约定实现

- 提示词给出的「项目工作目录」就是项目管理里为本项目绑定的代码仓库，也是本轮 cwd；动手前先加载该目录下的项目开发技能。
- 后端改动遵循 `backend-development`，前端改动遵循 `web-development`；这两个项目技能定义了分层、目录归属、封装和命名的硬约束。
- 严格落在文档的「需交付的内容」范围内；顺手发现的其他问题记录下来，不要夹带无关重构。
- 新代码要和周围代码风格一致：注释密度、命名、错误处理都照抄邻居的写法。
- 任务需求主目录 `doc/<模块>/<任务键>/`、设计文档目录 `doc/<模块>/<任务键>/design/` 和测试资产目录 `doc/test/<任务键>/` 都支持多份文档；新增说明、测试计划或补充材料使用独立文件名，不能覆盖主需求文档或既有测试用例。

## 4. 写下设计过程

本轮的设计过程写进 `doc/<模块>/<任务键>/design/`，**新建一份**文件名带可排序后缀的文档（例如 `设计过程-02.md`，序号接着目录里已有的最大序号往下排）。此前几轮的设计文档不要读、也不要改写——它们是历史记录，不是要维护成一份的活文档；只有本轮确实要延续其中某个结论时，才打开那一份、只引用需要的段落。

篇幅按本轮改动体量分档，不要一律照最长的写——输出 token 比缓存输入贵几十倍，小改动写六节是纯浪费：

- **小改动**（单文件、样式/文案/字段级调整、无方案分歧）：一屏以内。写清楚：需求怎么理解、为什么这么改、改了哪些文件、怎么验的。勘察到的现状不用复述，代码本身就是。
- **中等改动**（跨文件、新增接口或页面、有过取舍）：加上「考虑过哪些方案、各自代价、为什么选中这个、否决的理由」，以及影响面和兼容性。
- **大改动**（跨层、改数据结构或表、影响既有调用方）：完整六节——需求理解、勘察到的现状事实（附路径）、候选方案与取舍、选型理由、方案怎么落到具体改动、验证方式与遗留风险。

判断不了属于哪一档时，看改动涉及几个文件、有没有真的在两种做法之间犹豫过。写完在最终回复里用 Markdown 链接给出本轮这份文档的工作区相对路径。

## 5. 自验

交付前自己先验，不要把验证推给测试阶段：

- 能编译/类型检查/跑测试的就跑，**并且只跑改动涉及的范围**：`go build ./service/xxx/...` 而不是 `./...`，跑相关单测而不是全量。
- 所有验证命令的输出都要截断：`go build ./... 2>&1 | tail -30`、`npx tsc --noEmit 2>&1 | head -40`。要看的是有没有错、错在哪一行，不是完整日志。
- 界面类改动用项目的预览方式实际看一眼，别只凭代码推断。
- 验证失败就修，修不动就明确写成阻塞项，不要谎报通过。

## 6. 结束本轮

最终回复会存进任务的「动作执行产物」（面板的「设计文档」页签）。桥接器按回合累积，追加回合接在既有产物后面而不是覆盖它，所以本轮只写本轮的交付说明，不必复述前几轮：

1. **改了什么**：按文件列出新增、修改、删除，以及每处的意图；并给出本轮设计过程文档的路径。
2. **怎么验的**：跑过的命令和结果，含失败项。
3. **对照验收标准**：文档里的每条验收标准，说明已满足、部分满足还是未覆盖。
4. **测试交接信息**：测试入口、需要的环境变量/账号角色/夹具或样本数据、接口或业务执行顺序、可观察结果及清理方式；只写安全来源和用途，不写任何密钥或密码。
5. **遗留与风险**：未做的部分、已知限制、给测试阶段的提醒。

批量或顺序执行时，再加一节 `## 代码事实交接`：把**下游任务不必重新勘察一遍**的硬事实列成不超过 15 条要点——文件路径与行号、接口/函数签名、字段名与类型、表名与关键列、已定下的命名或分层约定。只写事实，不贴代码正文，不复述设计过程；桥接器会把这一节原样传给同队列的后续任务。

生成了用户需要查看或下载的文件、文档、图片时，在最终回复里用 Markdown 链接列出工作区相对路径。无法完成时明确写出阻塞原因和已完成的部分，不要假装做完。
