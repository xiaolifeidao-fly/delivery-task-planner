# 动作执行阶段

任务面板四个技能中的第三个，负责单条任务的 `phase=development` 回合。

| 技能 | 负责 |
| --- | --- |
| `delivery-task-planner` | 把需求拆成任务并写入面板 |
| `delivery-requirement-grooming` | 把一条任务梳理成需求文档 |
| **`delivery-action-execution`** | **本技能：按文档实现并交付产物** |
| `delivery-testing-report` | 验收产物并产出测试报告 |

## 会话前提

- 这一轮由任务面板的执行桥发起，任务已经被领取并绑定到当前会话。
- 不要调用 `claim_next_task`、`bind_task_execution_session`、`finish_execution_task` 或任何任务状态流转工具；桥接器按本回合的最终状态自动同步面板，并把最终回复保存为该任务的「动作执行产物」。
- 不要执行 `create-task-board-*` 动作创建任务；发现缺口写进最终回复的「后续建议」。
- 阶段推进（动作执行 → 成品测试）由用户在面板上操作，本轮不要顺手把测试报告写了。

## 1. 按提示词给出的顺序取需求

需求文档存不存在，桥接器已经在应用层核对过并写在提示词里，**不要自己再判断、也不要去试探性地读不存在的文件**。按提示词给出的这份顺序取需求：

1. **需求级文档** `doc/requirements/<需求键>/需求大纲.md`：提示词说它存在时，这是优先级最高的上下文，动手前先完整读一遍，目标、范围、约束和验收口径以它为准。
2. **任务级需求文档** `doc/<模块>/<任务键>/文档.md`：提示词说它存在时，接着完整读一遍，它补充本任务范围内的细节；与需求级文档冲突时以需求级文档为准，并在最终回复里指出冲突点。
3. **任务说明**：提示词说任务级需求文档不存在时，提示词里的「任务说明」就是本任务级需求的全部来源，直接按它执行——不要因为缺文档停下，也不要在动手前先补一份需求文档。

- 需求与代码现状明显不符时，先说明差异；小的出入按代码事实实现并在回复中记录，方向性冲突则停下来说清楚，不要自作主张改需求。
- 提示词还会给出「本需求下其他任务已写好的需求文档」清单，按需加载：标了「前置依赖」的先读（本任务要对接的接口和字段在那里），其余按标题挑与本任务真正相关的读，无关的不要打开。
- 批量或顺序执行时提示词会带上前置任务的约束条件说明，那是上游任务的实际产出，优先级高于文档里的推测。
- 用户在本会话里追加需求时，需求文档也要跟着更新：先完整读一遍现有文档，把追加的内容合并进对应章节后整篇写回同一路径；不要只把追加的那段写进文件，那会把之前的需求文档整段删掉。

## 2. 按项目约定实现

- 提示词给出的「项目工作目录」就是项目管理里为本项目绑定的代码仓库，也是本轮 cwd；动手前先加载该目录下的项目开发技能。
- 后端改动遵循 `backend-development`，前端改动遵循 `web-development`；这两个项目技能定义了分层、目录归属、封装和命名的硬约束。
- 严格落在文档的「需交付的内容」范围内；顺手发现的其他问题记录下来，不要夹带无关重构。
- 新代码要和周围代码风格一致：注释密度、命名、错误处理都照抄邻居的写法。
- 任务设计文档目录是 `doc/<模块>/<任务键>/design/`，支持多份文档；本轮的设计过程文档写在这里（见第 3 节），使用稳定、唯一的文件名，并在动作执行产物中给出路径。动作执行产物本身仍作为面板的兼容回退内容保留。
- 任务需求主目录 `doc/<模块>/<任务键>/` 以及测试资产目录 `doc/test/<任务键>/` 同样支持多份 Markdown、纯文本或 HTML 文档；新增说明、测试计划或补充材料时使用独立文件名，不能覆盖主需求文档或既有测试用例。

## 3. 写下整个设计过程

任务的文档产物不是改动清单的存档，而是**你这一轮完整的设计与思考过程**。写进 `doc/<模块>/<任务键>/design/` 下一份稳定命名的文档（例如 `设计过程.md`），至少覆盖：

1. **需求怎么理解**：从需求级文档、任务级文档或任务说明里读到的目标和边界，你的复述。
2. **勘察到的现状事实**：相关文件、接口、表、既有实现和它们的约束，附路径。
3. **考虑过哪些方案**：每个方案的做法、代价和风险，包括最后没选的那些。
4. **为什么选中最终方案**：判断依据，以及被否决方案的否决理由。
5. **方案怎么落到改动**：拆到具体文件和步骤，影响面、兼容性和数据迁移怎么处理。
6. **怎么验证、还剩什么风险**：验证方式与遗留项。

已有同名文档时先完整读一遍，把本轮推演补进去，不要整篇覆盖掉此前的设计过程。写完在最终回复里用 Markdown 链接给出它的工作区相对路径。

## 4. 自验

交付前自己先验，不要把验证推给测试阶段：

- 能编译/类型检查/跑测试的就跑（例如 `go build ./...`、`npx tsc --noEmit`、相关单测），并如实报告结果。
- 界面类改动用项目的预览方式实际看一眼，别只凭代码推断。
- 验证失败就修，修不动就明确写成阻塞项，不要谎报通过。

## 5. 结束本轮

最终回复会存进任务的「动作执行产物」（面板的「设计文档」页签）。桥接器按回合累积，追加回合会接在既有产物后面而不是覆盖它，所以本轮只写本轮的交付说明，不必复述前几轮：

1. **改了什么**：按文件列出新增、修改、删除，以及每处的意图；并给出本轮设计过程文档的路径。
2. **怎么验的**：跑过的命令和结果，含失败项。
3. **对照验收标准**：文档里的每条验收标准，说明已满足、部分满足还是未覆盖。
4. **测试交接信息**：测试入口、需要的环境变量/账号角色/夹具或样本数据、接口或业务执行顺序、可观察结果及清理方式；只写安全来源和用途，不写任何密钥或密码。
5. **遗留与风险**：未做的部分、已知限制、给测试阶段的提醒。

生成了用户需要查看或下载的文件、文档、图片时，在最终回复里用 Markdown 链接列出工作区相对路径。无法完成时明确写出阻塞原因和已完成的部分，不要假装做完。
