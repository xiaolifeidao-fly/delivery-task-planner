# 测试用例与成品测试

测试包含两个严格隔离的模式：先设计可执行测试用例，再由明确指令启动真实验证。测试不是复述动作执行结果：真实验收必须准备可用输入、按真实依赖顺序执行，并将可观测结果与验收标准比对。

| 技能 | 负责 |
| --- | --- |
| `delivery-task-planner` | 把需求拆成任务并写入面板 |
| `delivery-requirement-grooming` | 把一条任务梳理成需求文档 |
| `delivery-action-execution` | 按文档实现并交付产物 |
| **`delivery-testing-report`** | **本技能：准备、执行、验收并报告测试** |

## 会话前提

- 这一轮由任务面板的执行桥发起，任务已经被领取并绑定到当前会话。
- 不要调用 `claim_next_task`、`bind_task_execution_session`、`finish_execution_task` 或任何任务状态流转工具；桥接器会保存最终回复，并根据本报告的「验收判定」同步任务状态。
- 报告正文超过 8MB 会被面板拒绝：大块日志只留关键片段，完整日志落成工作区文件再用链接引用。
- 不把生产环境当测试环境；不暴露 Token、密码、Cookie、私钥或个人数据。报告只记录凭据的用途、来源类型和是否可用，例如“测试管理员账号（环境变量，已可用）”。

## 选择本轮模式

桥接提示词会明确写出本轮是以下哪一种模式；不得自行把一种模式升级成另一种。

| 模式 | 允许的工作 | 严禁做的事 | 结束产物 |
| --- | --- | --- | --- |
| **测试用例设计模式** | 读任务文档、代码、路由、调用链、既有动作产物和验收标准；设计范围、准备清单、数据、顺序、步骤、预期和证据 | 调接口、UI 自动化、脚本、构建命令或任何真实验证；写测试报告或验收判定；改业务实现或任务状态 | `测试用例.md`、按需 `测试计划.md` |
| **执行验收模式** | 先读已有测试用例，再准备环境并真实验证、取证、判定和报告 | 将未执行或无证据的结果写成通过 | `测试报告.md`、脚本、夹具和证据 |

### 测试用例设计模式

1. 完整读 `doc/<模块>/<任务键>/文档.md`，按真实代码、路由、前端调用、现有测试和关联任务建立测试对象；研发尚未完成的部分标为“执行前置/待补输入”，不可猜造实现结果。
2. 逐条拆验收标准，形成用例表：**编号 / 关联验收项 / 对象类型 / 前置与数据 / 操作顺序 / 预期 / 证据要求 / 执行前置**。接口必须列方法、鉴权来源类型、依赖实体、请求样例形状和关键断言；UI 列账号角色、初始状态和页面路径；脚本/媒体列输入、输出和核验方式。
3. 将跨接口、跨任务和端到端链路按真实依赖排序；明确 Token、账号、环境、测试数据、外部依赖、素材和清理方案的缺口。凭据只写来源类型，绝不写值。
4. 写入 `doc/test/<任务键>/测试用例.md`，按需写 `测试计划.md`。此模式只允许设计文档；不要创建 `测试报告.md`、脚本、夹具或证据文件。
5. 最终回复第一行必须且只能是：`测试用例已生成`。随后简述已覆盖范围、用例数量、执行顺序和待补条件；不要给出“验收判定”。

其余章节仅适用于**执行验收模式**。

## 测试资产目录

本次测试产生或整理的交付资产，一律放在**项目工作目录**下的 `doc/test/<任务键>/`；`<任务键>` 必须使用面板给出的任务编号（`itemKey`），不可按标题、模块名或日期另起目录。先创建该目录，再开始准备和执行测试。

按实际需要落盘，不创建空目录：

```text
doc/test/<任务键>/
├── 测试用例.md       # 研发并行时先生成；执行测试前必须读取
├── 测试计划.md       # 对象、输入、顺序、预期和准备结果
├── 测试报告.md       # 与面板最终报告一致的完整测试结论
├── scripts/          # 本任务一次性或可复用的测试脚本
├── fixtures/         # 脱敏、可复现的测试输入和配置样本
└── evidence/         # 截图、脱敏响应、日志、输出样本或媒体检查结果
```

- 所有新建的接口调用脚本、UI 自动化脚本、测试说明、计划、报告、夹具和证据都放在这个任务目录，并在报告中链接它们。
- 产品本身长期维护、需要纳入 CI 的单元/集成测试代码仍放在项目既有测试目录，以保持项目约定；在 `测试计划.md` 中记录其真实路径和本任务如何执行它。
- 文件名使用稳定、可读的中文或英文名称；不得写入真实凭据、未脱敏生产数据或与本任务无关的文件。

## 1. 建立测试范围与可验收口径（执行验收模式）

1. 完整读 `doc/<模块>/<任务键>/文档.md`，将「验收标准」拆成可检查条目：**条件/输入、操作、预期结果、观测方式**。不能量化的“正常”“可用”“效果好”要依据设计稿、代码约束或用户约定补成可判断的口径；仍无法确定则标为待确认。
2. 检查动作执行阶段实际交付：`git status`、`git diff`、动作执行产物、相关前置任务文档。文档与实际不一致时，两边都纳入范围并在报告说明差异。
3. 按需加载同一需求中有接口、数据口径、文件产物或前置依赖关系的文档；不要为凑上下文通读无关任务。
4. 从真实代码、OpenAPI/路由、前端调用、现有测试、脚本入口、构建配置或交付说明中建立「测试对象清单」，不要凭任务标题猜接口、页面或文件。

每个测试对象至少记录：对象、类型、入口或路径、前置条件、输入/样本、预期结果和证据位置。

## 2. 准备测试输入与环境（执行验收模式）

把准备工作当成测试的一部分，先完成并记录其结果，再执行用例。

- **接口/服务**：确认环境地址、接口列表和业务依赖；为每个接口列出方法、鉴权方式、请求数据、依赖数据、预期状态码与关键字段。Token 只从已配置的测试环境、受控环境变量或用户明确提供的安全渠道读取，绝不猜造、输出或复用任务面板登录 Token。
- **UI**：确认可访问地址、测试账号及角色、必要初始状态和浏览器/设备条件。凭据未提供时，记录缺哪个角色或能力；不要尝试绕过登录或使用未知账号。具备可用自动化能力时，用项目既有脚本或浏览器自动化执行，并留截图、录屏或可复查的页面证据。
- **脚本、批处理、数据任务**：准备版本化输入文件、配置、运行参数、隔离目录及清理方案；明确输出文件、日志、数据库记录或副作用的核对方法。
- **视频、图像、文档等交付物**：准备源素材、脚本/字幕/时间轴或版式输入、导出配置和播放/打开环境；明确时长、分辨率、帧率、音轨、字幕、画面节点、可读性或文件格式等可验收指标。
- 优先使用测试夹具、临时账号、可回滚数据和隔离环境。确需写入时，记录创建对象、回滚/清理动作及结果；不对生产数据做破坏性测试。

缺少关键环境、账号、密钥、素材、依赖服务或测试数据时，先尽力从仓库的受控配置、测试夹具和已有说明中确认；仍缺失就停止受影响的用例，写清最小补充项，不用虚构数据得出“通过”。

## 3. 编排并执行测试路径（执行验收模式）

先从代码和业务依赖确定顺序，再执行；不要把互相依赖的接口或页面随意打散。

1. 先验证基础可用性：服务/页面/脚本可启动，必要依赖和鉴权可用。
2. 再沿主业务路径验证上游到下游的链路。接口通常是“鉴权或身份 → 查询/准备依赖实体 → 创建或触发动作 → 查询/消费结果 → 断言副作用 → 清理”；实际顺序以代码和业务约束为准。
3. 覆盖验收标准涉及的正常路径、边界值、错误路径、权限边界、幂等/重复执行及前后端或任务间联动。只测与本任务有关的最小集合，不做无关全量回归。
4. 每个用例都留下输入摘要、执行步骤、实际结果和证据。接口保留脱敏请求摘要、响应状态/关键字段及关联日志；UI 保留操作路径和截图；脚本/产物保留命令、输出及文件或媒体检查结果。

在提示词给出的项目工作目录执行验证，并先加载该目录的项目开发技能，沿用项目约定的测试、构建和 UI 验证方式。开始前先读取 `doc/test/<任务键>/测试用例.md`；测试准备完成后及时写 `doc/test/<任务键>/测试计划.md`；生成的脚本、夹具和证据随用例写入该目录，不要散落在临时目录或项目根目录。

## 4. 按验收标准判定（执行验收模式）

逐条将实际观测结果与验收标准的预期值对比，给出：**通过 / 不通过 / 未覆盖**。

- **通过**：已执行，实际结果与预期一致，且有可复查证据。
- **不通过**：已执行但结果不符。写清复现步骤、期望与实际、影响面、关联输入/数据，以及建议修复位置；本阶段只判定和定位，不顺手改实现。
- **未覆盖**：因缺环境、账号、Token、测试数据、外部依赖或验收口径无法执行。写明缺少什么、由谁/在哪里补充、补齐后应执行哪条用例。

最终判定规则：所有必要验收标准通过才是「通过」；任何必要项不通过是「不通过」；没有不通过但仍有必要项未覆盖或关键前置缺失是「受阻」。

## 5. 结束本轮（执行验收模式）

完成测试后，先把完整报告写入 `doc/test/<任务键>/测试报告.md`，再将同一份结论作为最终回复；最终回复会保存到任务面板。**第一行必须且只能写以下之一**，供执行桥同步任务状态：

```text
验收判定：通过
验收判定：不通过
验收判定：受阻
```

随后按以下结构报告：

1. **测试摘要**：测试对象、环境、已准备的账号/数据/素材（均脱敏）和测试顺序。
2. **测试准备**：环境、鉴权、测试数据、账号/角色、依赖服务、清理结果；缺失项也在此列出。
3. **执行用例**：表格列「测试对象 / 输入与前置 / 操作顺序 / 预期 / 实际 / 证据」。
4. **验收标准逐条结果**：表格列「验收标准 / 结论 / 实际结果 / 证据」。
5. **缺陷与受阻项**：复现步骤、期望与实际、影响面、建议修复或补充项。
6. **风险与清理**：未覆盖范围、遗留风险，以及测试数据和临时资源的清理情况。

生成的截图、日志、输入/输出样本、视频或其他文件，全部存入 `doc/test/<任务键>/` 并用 Markdown 链接列出其工作区相对路径。没有证据、测试输入或明确口径，不得写“通过”。
