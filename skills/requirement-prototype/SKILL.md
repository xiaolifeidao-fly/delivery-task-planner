# 需求 HTML 原型

## 适用范围

- 当前聊天已绑定需求和项目工作区时，任何一轮对话都可以直接生成或修改该需求的 HTML 原型；无需要求用户切换到专门的原型入口、创建新窗口或重复确认。
- 用户可以在需求讨论、任务拆解或后续补充的任意聊天中提出原型意见。收到明确的原型请求后，直接落地文件，不要只回复操作建议。
- 原型只服务当前需求。缺少需求编号或项目工作区，且无法从会话上下文确定时，先询问这两项；不要猜测或修改其他需求的原型。
- 只修改需求原型目录及其 HTML 文件；除非用户明确提出，不能顺带改业务代码、配置、依赖或任务数据。

## 固定存放与关联

- 原型唯一权威副本位于项目工作区：`doc/requirements/<需求编号>/prototype/`。`<需求编号>`必须使用当前需求的 `requirementKey`。
- 每次生成、追加或修改后，都必须实际更新这个目录中的 HTML 文件；不得只在聊天正文中给出代码或把文件写到临时目录。
- 完成后必须让该目录与当前需求关联。通过任务面板桥接运行时，桥接器会在确认 HTML 文件存在后回写需求的原型路径和生成时间；最终回复仍要列出实际相对路径，方便桥接器和用户核对。不要在文件未落盘时声称已关联。
- 编辑既有原型时先阅读相关页面，保留本轮未要求改变的内容；需要删除页面时，确认没有其他页面的入口依赖后再删除。

## HTML 拆分规则

- 必须按功能模块或用户流程拆分为多个独立 HTML 文件，不能把整份需求原型堆在单一 HTML 中。
- 至少提供 `index.html` 作为入口或总览，再按功能放入页面，例如 `overview.html`、`member-management.html`、`approval-flow.html`。即使需求较小，也要把总览和核心操作拆开。
- 每个 HTML 页面都应可单独在浏览器打开，并能清楚知道其上下游页面；`index.html` 提供各模块入口，跨页面跳转使用相对路径。
- 优先使用内联 CSS/JS 或同一原型目录内的本地资源，避免远程依赖；使用 UTF-8 编码，保证面板能安全预览每个页面。

## 设计与交互标准

- 交付美观、大方、成熟且操作体验良好的原型，而不是只有控件堆砌的线框图。保持清晰的信息层级、留白、对齐、统一的颜色/字体/圆角/状态样式，以及适度的视觉反馈。
- 使用接近真实产品的内容、数据状态和错误/空状态；重要操作要有明确的主次关系、可见的反馈和可理解的撤销或返回路径。
- 考虑常用桌面宽度，并为窄屏保留可用的布局。表单、表格、筛选、分页、弹窗和多步骤流程要能演示关键交互，不只画静态页面。
- 修改时优先保持既有视觉语言和文件导航一致；用户要求改局部时，不要无故重做无关模块。

## 完成检查

- 在浏览器中检查入口页、各模块页和关键跳转；确认没有损坏链接、重叠内容或无法完成的核心操作路径。
- 确认原型目录中存在多个可预览的 `.html` / `.htm` 文件，并且本轮涉及的页面已经更新。
- 最终回复简短说明本轮改动、列出原型相对路径，并说明需求关联已由面板桥接同步；如果同步失败，如实报告原因和已落盘的文件。
