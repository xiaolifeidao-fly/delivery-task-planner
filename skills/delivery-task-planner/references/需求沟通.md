# 需求沟通：先把需求聊清楚

什么时候读：需求聊天处于沟通态（提示词里没有拆解契约）的每一轮。

需求聊天窗口发起的会话默认是**沟通态**，不是拆解态。桥接器只在该拆的那一轮才把拆解契约（任务表格式、任务说明规范、依赖分层）发给你；提示词里没有这些，就说明当前是沟通态。

- 沟通态要聊完整的是：需求目标与动机、范围边界与不做的事、真实落点、关键业务规则、验收口径、待确认问题。这一轮不要输出任务表、执行层、依赖图或工期计划，也不要提示「确认并写入」。
- 先给判断，再问问题：用户没说清的地方，先讲你的理解和你划的边界，把疑问和风险点标出来，再挑最影响交付范围、技术落点和验收口径的 1-3 个问题问用户。不要连问一长串，也不要用问题清单代替自己的判断。
- 能自己查的不要问：缺的工程事实按 SKILL.md 第 3 节的勘察纪律去工作区核实，把核实到的真实落点（具体模块、目录、接口、表、组件）讲给用户听。
- 用户还在补背景和想法时就跟着往下聊，不要急着收敛成方案；他说的和你勘察到的事实冲突时，直接指出来并确认以哪个为准。
- **主动引导**：当目标、范围边界、真实落点和验收口径都已经清楚、够开始拆任务了，在回复末尾主动问一句提示词里给出的那句引导语。**必须按提示词里的原文写**——桥接器靠字面匹配识别引导，改一个字就失效，用户下一轮回一句「好」也进不了拆解。还没到这一步就不要问，先把缺的部分补齐。
- **用户主动要拆**：用户随时可以说「拆一下」「生成任务」。这时立刻按 `references/任务拆解与写入.md` 给出可评审的拆解预览，不要再反问一遍；即使本轮提示词里还没带拆解契约，也照 `references/任务拆解与写入.md` 的规则拆，桥接器会在下一轮把契约补上。
- 拆解态一旦进入就不再退回沟通态：这条聊天窗口后续的追问都按拆解轮处理，输出规则见 `references/任务拆解与写入.md` 的增量约定。用户在拆解之后回头补需求背景，正常回应即可。
