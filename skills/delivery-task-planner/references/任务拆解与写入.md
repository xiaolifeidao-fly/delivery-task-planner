# 规划引擎：拆解任务与写入

什么时候读：用户要求拆解、接住了拆解引导，或本轮是确认写入轮。

## 拆解任务

根据已经聊清楚的需求、项目上下文和 SKILL.md 第 3 节勘察到的工程事实，生成可独立交付、可验证的任务：

- 每个任务包含短引用 `ref`、标题、描述、**收益标签**、里程碑、模块、类型和直接前置依赖；收益标签必须是 1–3 个简短词组，用来描述该任务完成后能带来的收益或作用（如“减少人工核对”“提升审核可追溯性”），不可为空也不要重复任务标题。描述（`description`）是动作执行阶段的兜底需求输入：任务没有单独的任务需求文档时，执行器唯一能看到的需求就是它，因此必须写成脱离本次聊天也能独立执行的说明。插件会把这些字段整理为可阅读的需求文档并随任务落库。
- 每条描述至少交代六件事：①要解决的问题和目标；②勘察到的真实落点（具体文件、目录、接口、表、组件，能给路径就给路径）；③要做的改动，分条列清；④边界与不做的事；⑤依赖与输入（前置任务产出、字段口径、配置或数据准备）；⑥可验证的验收标准。用短句分条写，正文控制在 300–1500 字，写满这六件事优先于压字数；要贴大段代码、接口清单或表结构就写进任务需求文档，不要塞进描述。
- 预览时在任务表下方逐条给出与实际写入一致的完整描述，让用户在点「确认并写入」前就看到执行器将拿到的原文。
- 这条只对一次拆解的**首轮**成立。同一个聊天窗口里的后续追问只给增量：任务表只列新增或被改动的行（序号后标「新增」「修改」），表格下方也只给这几条的完整描述，其余任务写一行「其余 N 条不变」即可。整份预览重印一次，既要花本轮的输出，又会留在会话历史里让后面每一轮跟着重读；用户明确要「再给一份完整预览」时才整份重印。
- 任务负责人必须与所属需求保持一致。写入时不在任务数组里填写负责人：插件会依据 `requirement_key` 读取该需求的主负责人，并把第一位主负责人写入每条任务的 `ownerId` / `ownerName`；需求没有主负责人时任务保持未指派。任务模型当前只支持一位负责人，因此需求存在多位主负责人时，预览和写入均以第一位为准。
- `kind` 只能是 `gap`、`capability` 或 `asset`，通常新工作用 `capability`，阻塞问题用 `gap`，已具备且只需登记的内容用 `asset`。
- 依赖只表达“前置任务完成后，本任务才能继续”，不要添加仅仅因为书写顺序产生的依赖。
- 依赖图必须按执行层规划：每层只能有 1–3 个可并行任务；超过 3 个时，优先合并同一交付面的细粒度工作，或调整拆解边界，不能为了凑并行度虚构依赖。
- 依赖只能引用本批任务的 `ref`，不能引用既有任务或其他需求的 `itemKey`；每条依赖只允许连接紧邻的上一执行层，不得跨层，也不得保留可由传递关系推导出的重复依赖。并行任务不要互相依赖。
- 先验证依赖图是有向无环图，再列出“第 N 层：任务 A、任务 B”的执行层预览；确认每层不超过 3 项后再展示任务表和请求写入。
- 避免创建与已有任务语义重复的任务。
- 需求可以关闭「拆解成多条任务」。提示词里出现 `拆解成多条任务: 否（只建一条任务）` 时，预览和写入都只能给出一条覆盖整条需求的任务，`depends_on` 传空数组；工具会拒绝多于一条的写入（原型任务由工具自己追加，不受此限制）。
- 任务标题和描述要落到勘察出来的真实模块、目录或接口上，不要停留在业务名词的泛化分层；能引用仓库路径就引用。
- 如果用户选择了里程碑，所有任务都使用该里程碑，不再自行分类。
- 如果用户选择了模块，所有任务都使用该模块，不再自行分类。
- 未选择里程碑或模块时，必须从项目现有选项中为每个任务判断归属；项目对应选项为空时才允许留空。

在写入前，用简洁表格展示任务、收益标签、负责人、里程碑、模块和前置依赖，并在表格下方补充每个任务的目标、范围和验收标准。追问轮同样只展示本轮的增量部分；确认写入那一轮再把开始拆解那一轮的全量预览和后续各轮增量叠加成最终一份提交，上下文里已经找不到早期轮次时，读提示词给出的过程总结文件核对。

写入需要用户明确确认：

- 任务面板发起的需求梳理会话默认是预览态：拆解轮只做梳理和预览，并提示用户确认无误后点击输入框旁的「确认并写入」；还停在沟通态的会话没有可确认的方案，面板会拒绝这时的确认写入。Codex 执行器下 `create-task-board-*` 系列动作会直接拒绝执行；Claude 执行器一律以 bypass 权限启动，命令行不拦截，「确认前不写入」全靠本条约束，更要严格遵守。
- 用户提出修改意见时继续调整预览，不要试图绕过拒绝去写入。
- 用户确认后，面板会再发起一轮带写入权限的会话，那一轮才调用写入工具。
- 在普通对话工作流里，用户直接说“拆解并写入”即为授权，展示计划后可以直接写入。

## 写入

执行一次 `"$TASKBOARD" create-task-board-tasks` 批量写入，传递项目表数值主键 `program_id`（不是项目名称或 `program_code`）、会话给出的 `requirement_key` 和 `phase`、可选的 `stage_key` / `module_key` 以及完整任务数组。会话已绑定项目时可以省略 `program_id`。

- 会话提示词给出 `requirement_key` 时必须原样传回：任务要挂回发起这次拆解的那条需求，否则需求列表点开看不到本次产出。
- `requirement_key` 同时是任务负责人继承的唯一依据。不要为单条任务编造或覆盖负责人；工具会从该需求读取并统一写入负责人。
- 提示词里的「本需求已建任务」是上一轮的产出，只补缺口，不要重建。
- 每次写入自动开一条**拆解批次**：本轮所有任务共享同一个 `planningBatchKey`，任务进度按批次成行展示，也按行整批「再做一次」。一次调用就是一批，不要为了分组把一轮拆解拆成多次调用。
- 可选 `planning_batch_title` / `planning_batch_summary` 说明这一批补的是什么；不传时服务端按「第 N 次拆解」命名。

- `depends_on` 只能引用本批任务的 `ref`，并且只可指向紧邻上一执行层的任务。
- 不自行生成 `item_key`，除非用户明确要求固定业务键；工具会生成不超过 64 字符的唯一键。
- 工具会再次强制应用用户选择的里程碑/模块、检查环和无效依赖，并按拓扑顺序创建。
- 如果部分写入后接口报错，明确列出已创建和未创建项；不要自动删除已创建任务。

完成后报告项目、创建数量、任务键和依赖关系，并带上返回的 `planningBatchKey` 与 `planningBatchSeq`（这是本轮任务在需求下的第几批）。`sessionBindingsPending` 表示这些任务仍等待宿主创建执行会话，不代表插件能够自行生成会话。不要声称写入成功，除非工具返回成功。
