# Delivery Task Planner

这是任务面板的建设与需求规划工作流。它只负责创建业务结构和任务，不负责运行任务。

任务面板的四个技能都维护在本插件的 `skills/` 下，按任务生命周期分工：

| 技能 | 负责 |
| --- | --- |
| **`delivery-task-planner`** | **本技能：把需求拆成任务并写入面板** |
| `delivery-requirement-grooming` | 单条任务的「梳理需求」阶段（phase=requirement） |
| `delivery-action-execution` | 单条任务的「动作执行」阶段（phase=development） |
| `delivery-testing-report` | 单条任务的「成品测试」阶段（phase=testing） |

后三个阶段技能由任务面板的执行桥在执行单条任务时使用，本技能不负责执行。

## 能力边界

- 可以创建项目、里程碑、模块和任务，也可以把需求拆解后批量写入。
- 不从 Codex 对话读取执行队列、领取任务、绑定执行会话、更新执行状态或结束任务。
- 用户要求“开始任务”“运行任务”“继续任务”时，不执行任务；明确告知必须前往任务面板点击执行入口。
- 任务面板可通过本地宿主桥接器调用 Codex，但这是任务面板内部能力，不是本插件向对话暴露的工具。
- 任务面板启动的桥接请求必须包含选中的 `programId`、当前浏览器已确认的 `workspace` 和当前登录用户的 `token`。项目范围只由数值主键确定；`workspace` 只决定本机 Codex 的工作目录，不得用它切换任务面板项目。不得保存面板 token，也不得允许子进程切换项目。
- 除本地项目发现接口外，桥接器不得使用安装目录或启动目录作为默认工作目录；请求缺少 `workspace` 时必须拒绝，并提示用户先到项目管理确认工作目录。

## 0. 怎么调任务面板

所有任务面板操作都用命令行执行：

```bash
"$TASKBOARD" <动作> [--参数 值 ...] [--json '<完整参数 JSON>']
```

先定好入口路径，插件根目录环境变量缺失时退回个人安装目录：

```bash
TASKBOARD="python3 ${CLAUDE_PLUGIN_ROOT:-$HOME/plugins/delivery-task-planner}/taskboard.py"
```

约定：

- 服务端地址写死在插件里（`http://47.110.3.214:8691/api`），不需要也不能配置。
- 凭证由控制台每分钟一次的心跳写入 `~/.config/delivery-task-planner/credential.json`，命令行自己会读；任务面板发起的会话则用注入的运行期凭证。不要在回复里展示完整 token。
- 成功时命令把结果 JSON 打到 stdout，失败时把原因打到 stderr 并以 1 退出；照原样读结果，不要臆造字段。
- 参数名和动作名都用连字符：`--program-id`、`get-task-board-context`。数组和对象参数（例如任务清单）走 `--json`，内容长时写成文件再用 `--json @/tmp/tasks.json`。
- `"$TASKBOARD" actions` 列出全部动作及其参数，拿不准时先看它，不要猜参数名。

## 1. 检查配置

先执行 `"$TASKBOARD" get-task-board-configuration`。

- 上述项目级约束适用于任务面板桥接运行态。
- 返回 `configured: false` 说明还没收到凭证：请用户在控制台登录并保持页面打开，等一次心跳（最多一分钟）；控制台确实跑不起来时，才用 `"$TASKBOARD" store-task-board-credential --key <token>` 手工写一次。
- 不要在回复中重复、展示或记录完整 key。

## 2. 创建或确定项目结构

用户明确要求新建项目、里程碑或模块时：

- 项目按**空间**（业务线）分片：先执行 `"$TASKBOARD" list-task-board-spaces` 看当前账号有哪些空间，拿到空间编码。
- 新建项目执行 `"$TASKBOARD" create-task-board-project`，要求所属空间 `--biz-line`、唯一 `program_code` 和项目名称；它会返回后续操作使用的数值主键 `programId`。
- 新建里程碑执行 `"$TASKBOARD" create-task-board-stage`，要求里程碑键、里程碑名称和里程碑目标；未指定顺序时追加到最后。
- 新建模块执行 `"$TASKBOARD" create-task-board-module`，要求模块键和模块名称；未指定顺序时追加到最后。
- 创建里程碑和模块前必须确定项目；不覆盖已有相同业务键。

拆解需求或创建任务时，按以下规则确定项目：

- 命令行参数 `--program-id` 一律传项目表数值主键（`programId`），任何情况下都不要传项目名称或 `program_code`。会话提示词给出的 `项目 program_id` 就是它；项目名称只用于向用户描述，不作为参数。
- 会话已经绑定项目时（从任务面板发起的拆解都属于这种），可以直接省略 `program_id`，命令行会用绑定的那个项目。
- 用户用名称指代项目时，先用 `"$TASKBOARD" list-task-board-projects` 换成 `programId` 再执行命令。不带参数时它会遍历全部可见空间并合并，每条项目带回自己的 `bizLine`；只看某个空间时加 `--biz-line <空间编码>`。
- `programCode` 会跨空间重名（同一个 `test` 可能同时存在于多个空间），认项目只认 `programId`，展示给用户时带上空间名以免选错。
- 如果当前执行器没有关联项目，执行 `"$TASKBOARD" list-task-board-projects` 展示项目并要求选择；匹配失败时展示可选项目，不得创建同名新项目。

规划需求时还必须得到：

- 里程碑：可选，只能从所选项目的里程碑中选择。
- 模块：可选，只能从所选项目的模块中选择。
- 需求内容：必填。

如果用户已经在同一条消息中给出这些信息，直接校验，不重复询问。里程碑和模块未输入时保持可选，不要强制追问。

选定项目后执行 `"$TASKBOARD" get-task-board-context`，同时传入用户选择的里程碑和模块。该动作会校验选择，并返回已有任务供去重和依赖分析。

注意：`get-task-board-context` 只给出任务面板侧的上下文（里程碑、模块、已建任务），不包含工程现状。工程现状要自己去工作区读，见下一节。

## 3. 勘察工作区现状

拆解之前先看代码，否则只能按需求里的业务名词泛化出一套"领域模型 → 列表 → 详情 → 导出 → 联调"的通用瀑布流，和真实工程对不上。

本节只读不写，是拆解的前置动作，不可跳过：

- 从任务面板发起时，会话提示词里会给出「项目工作目录」——那是项目管理中为该项目绑定的代码仓库，也是本轮的 cwd，直接在那里勘察。
- 先加载项目自己的开发技能（后端看 `backend-development`，前端看 `web-development`，以工作区实际存在的为准），据此理解分层、目录约定和依赖方向。
- 定位需求涉及的实际落点：相关目录、已有页面或接口、命名与分层约定、可复用的既有实现。
- 找出与需求重叠或冲突的既有实现——这些应该拆成改造任务，而不是新建任务。

如果工作区里找不到需求所指的模块（例如需求说"新管理端"但工作区没有对应目录），不要凭业务名词硬拆，先向用户说明并确认工作目录或范围。

## 4. 最终需求文档与过程摘要

每条需求在工作区里有且只有一份最终需求大纲：`doc/requirements/<requirement_key>/需求大纲.md`。任务面板的需求侧栏「需求大纲」页签直接预览这个文件，它只保存用户最终确认的需求产物，不承载讨论过程。

- 预览、追问和调整阶段，最终需求大纲一律只读：存在时可读取已确认内容，不存在时不得创建；不能把过程数据、未确认方案、聊天流水或每轮预览写进去。
- 每个聊天窗口的最新过程总结由桥接器自动覆盖写入插件安装目录：`.temp/requirements/req_<需求名称>/<聊天窗口ID>/temp.md`。它不是项目交付物，也不登记到任务面板。正常连续对话直接使用当前聊天上下文，不重复读取；只有会话被压缩、恢复后上下文缺失时才读取它作为恢复点。
- 用户每次输入完成后，`temp.md` 保存本轮用户输入和当前总结性产物；同一聊天窗口整篇刷新，不把临时数据拆散到正式需求目录。
- 只有用户点击「确认并写入」，本轮才可以更新最终需求大纲。确认写入属于必须读取 `temp.md` 的例外：写入前完整读取既有最终大纲和当前聊天的过程总结，只合并最终确认内容，排除被否决方案和未确认草稿，再整篇覆盖。确认回合成功完成后，桥接器删除当前聊天窗口的 `temp.md`；确认失败或中断时保留，供恢复和重试。
- `temp.md` 是候选材料，不是最终文档模板。确认写入时必须先分析、去重和重组，只沉淀对需求目标、交付范围、关键业务规则、实现约束、验收标准、测试准备或最终决策有实际价值的已确认内容；写成可执行、可验证的需求表述，不能整段复制聊天总结。
- 最终文档不保留寒暄、重复确认、讨论流水、未采纳备选、无结论推演、工具日志或聊天元信息；但不能以“精简”为由遗漏已确认的非目标、兼容性要求、异常与边界场景、风险约束或仍影响交付的待确认问题。
- 最终大纲至少包含：需求背景与目标、范围与不做的事、关键约束、勘察到的落点（真实模块/目录/接口）、任务拆解表（与实际落库一致）、验收标准、待确认问题。
- 用户明确要求生成的独立 HTML、流程图、图表和其他正式附件仍按下节写入需求文档目录，不受最终大纲延迟写入规则影响。

### 独立需求资产

需求编辑中，需求大纲之外的独立流程图、图表、HTML 或其他需求附件统一写入
`doc/requirements/<requirement_key>/` 这个需求文档目录，并使用独立文件名。该目录支持多份文档，`需求大纲.md` 只是主文档；只有用户明确要求生成或更新独立文件时才创建这些资产；
不要把项目交付文件写到 `.codex/visualizations`、系统临时目录或其他工作区外路径，也不要把独立文件正文强行嵌入需求大纲。
不要把 `visualize` 工具的默认输出路径当成交付路径；如果它先生成了临时预览，必须把最终文件复制到上述需求目录后再回复目标路径。
完成后在回复中列出工作区相对路径，便于面板登记和预览。

需求原型统一放在同一需求目录的 `prototype/` 下，允许多个独立 `.html` / `.htm` 页面；需求级测试资产统一放在 `doc/test/<requirement_key>/`，允许 `测试用例.md`、`测试计划.md`、`测试报告.md` 和其他补充文档各自并存。除这些固定栏目目录外，不要另起同需求的临时文档目录。

### 被 @ 引用的历史需求

需求详情里可以用 `@` 引用之前的需求（正文里保存成 `@[需求名](requirement:需求键)`）。提示词只会给出这些需求各自的需求大纲产物地址，**不会**附上正文。

- 需要背景时按给出的路径自行读取，且只读与当前需求真正相关的章节；不要为了凑上下文把整份大纲搬进回复。
- 路径对应的文件不存在，说明那条需求还没沉淀大纲：如实说明，不要臆造。
- 引用只是背景和既有约定的来源，本轮拆解的范围仍然只限当前这条需求，不要顺手把被引用需求的遗留项拆成任务。

### 预生成任务需求文档

任务没有第二份“任务需求大纲”。`doc/<module_key>/<item_key>/文档.md` 是任务从梳理到执行唯一的需求文档，任务详情和看板入口展示、编辑的也是它。

- 默认不预生成：关闭时，由任务的「梳理需求」阶段首次创建这份文档。
- 需求上打开「预生成任务需求文档」时，只在确认写入那一轮处理：`create-task-board-tasks` 返回每条任务的 `moduleKey`、`itemKey` 和 `requirementDocumentPath` 后，为本轮**每条**新建任务创建或覆盖该路径对应的文档，一条任务一个文件，不要另建大纲。
- 需求关闭「拆解成多条任务」时，不需要再打开预生成开关：确认写入后只有一条 `prototypeTask=false` 的业务任务，必须把本轮完整需求文档直接创建或覆盖到它返回的 `requirementDocumentPath`。需求级大纲仍保留规划历史，但不能代替任务文档；若同时生成原型图，不要把需求正文写进原型任务文档。
- 预生成的是可实施初稿，至少包含：任务目标、范围与不做的事、已知落点（真实模块/目录/接口）、实现要点、前置依赖、验收标准与待确认项；不能把任务卡片的一两句描述当成完整文档。
- 后续任务「梳理需求」必须先读这份初稿，保留已确认结论、基于真实工程事实校正和补全，仍然只写回同一路径（同样是先读全文再整篇合并写回，不能只写增量）。预览轮不要创建这些文件，最终总结里列出实际写入的需求文档路径。

## 5. 规划引擎：拆解任务

根据需求、项目上下文和上一节勘察到的工程事实生成可独立交付、可验证的任务：

- 每个任务包含短引用 `ref`、标题、描述、**收益标签**、里程碑、模块、类型和直接前置依赖；收益标签必须是 1–3 个简短词组，用来描述该任务完成后能带来的收益或作用（如“减少人工核对”“提升审核可追溯性”），不可为空也不要重复任务标题。描述（`description`）是动作执行阶段的兜底需求输入：任务没有单独的任务需求文档时，执行器唯一能看到的需求就是它，因此必须写成脱离本次聊天也能独立执行的说明。插件会把这些字段整理为可阅读的需求文档并随任务落库。
- 每条描述至少交代六件事：①要解决的问题和目标；②勘察到的真实落点（具体文件、目录、接口、表、组件，能给路径就给路径）；③要做的改动，分条列清；④边界与不做的事；⑤依赖与输入（前置任务产出、字段口径、配置或数据准备）；⑥可验证的验收标准。用短句分条写，正文控制在 300–1500 字，写满这六件事优先于压字数；要贴大段代码、接口清单或表结构就写进任务需求文档，不要塞进描述。
- 预览时在任务表下方逐条给出与实际写入一致的完整描述，让用户在点「确认并写入」前就看到执行器将拿到的原文。
- 任务负责人必须与所属需求保持一致。写入时不在任务数组里填写负责人：插件会依据 `requirement_key` 读取该需求的主负责人，并把第一位主负责人写入每条任务的 `ownerId` / `ownerName`；需求没有主负责人时任务保持未指派。任务模型当前只支持一位负责人，因此需求存在多位主负责人时，预览和写入均以第一位为准。
- `kind` 只能是 `gap`、`capability` 或 `asset`，通常新工作用 `capability`，阻塞问题用 `gap`，已具备且只需登记的内容用 `asset`。
- 依赖只表达“前置任务完成后，本任务才能继续”，不要添加仅仅因为书写顺序产生的依赖。
- 依赖图必须按执行层规划：每层只能有 1–3 个可并行任务；超过 3 个时，优先合并同一交付面的细粒度工作，或调整拆解边界，不能为了凑并行度虚构依赖。
- 依赖只能引用本批任务的 `ref`，不能引用既有任务或其他需求的 `itemKey`；每条依赖只允许连接紧邻的上一执行层，不得跨层，也不得保留可由传递关系推导出的重复依赖。并行任务不要互相依赖。
- 先验证依赖图是有向无环图，再列出“第 N 层：任务 A、任务 B”的执行层预览；确认每层不超过 3 项后再展示任务表和请求写入。
- 避免创建与已有任务语义重复的任务。
- 需求可以关闭「拆解成多条任务」。提示词里出现 `拆解成多条任务: 否（只建一条任务）` 时，预览和写入都只能给出一条覆盖整条需求的任务，`depends_on` 传空数组；工具会拒绝多于一条的写入（原型任务由工具自己追加，不受此限制）。
- 任务标题和描述要落到勘察出来的真实模块、目录或接口上，不要停留在业务名词的泛化分层；能引用仓库路径就引用。
- 如果用户选择了里程碑，所有任务都使用该里程碑，不再自行分类。
- 如果用户选择了模块，所有任务都使用该模块，不再自行分类。
- 未选择里程碑或模块时，必须从项目现有选项中为每个任务判断归属；项目对应选项为空时才允许留空。

在写入前，用简洁表格展示任务、收益标签、负责人、里程碑、模块和前置依赖，并在表格下方补充每个任务的目标、范围和验收标准。

写入需要用户明确确认：

- 任务面板发起的需求梳理会话默认是预览态：此时只做梳理和预览，并提示用户确认无误后点击输入框旁的「确认并写入」。Codex 执行器下 `create-task-board-*` 系列动作会直接拒绝执行；Claude 执行器一律以 bypass 权限启动，命令行不拦截，「确认前不写入」全靠本条约束，更要严格遵守。
- 用户提出修改意见时继续调整预览，不要试图绕过拒绝去写入。
- 用户确认后，面板会再发起一轮带写入权限的会话，那一轮才调用写入工具。
- 在普通对话工作流里，用户直接说“拆解并写入”即为授权，展示计划后可以直接写入。

## 6. 规划引擎：写入

执行一次 `"$TASKBOARD" create-task-board-tasks` 批量写入，传递项目表数值主键 `program_id`（不是项目名称或 `program_code`）、会话给出的 `requirement_key` 和 `phase`、可选的 `stage_key` / `module_key` 以及完整任务数组。会话已绑定项目时可以省略 `program_id`。

- 会话提示词给出 `requirement_key` 时必须原样传回：任务要挂回发起这次拆解的那条需求，否则需求列表点开看不到本次产出。
- `requirement_key` 同时是任务负责人继承的唯一依据。不要为单条任务编造或覆盖负责人；工具会从该需求读取并统一写入负责人。
- 提示词里的「本需求已建任务」是上一轮的产出，只补缺口，不要重建。
- 每次写入自动开一条**拆解批次**：本轮所有任务共享同一个 `planningBatchKey`，任务进度按批次成行展示，也按行整批「再做一次」。一次调用就是一批，不要为了分组把一轮拆解拆成多次调用。
- 可选 `planning_batch_title` / `planning_batch_summary` 说明这一批补的是什么；不传时服务端按「第 N 次拆解」命名。

- `depends_on` 只能引用本批任务的 `ref`，并且只可指向紧邻上一执行层的任务。
- 不自行生成 `item_key`，除非用户明确要求固定业务键；工具会生成不超过 64 字符的唯一键。
- 工具会再次强制应用用户选择的里程碑/模块、检查环和无效依赖，并按拓扑顺序创建。
- 如果部分写入后接口报错，明确列出已创建和未创建项；不要自动删除已创建任务。

完成后报告项目、创建数量、任务键和依赖关系，并带上返回的 `planningBatchKey` 与 `planningBatchSeq`（这是本轮任务在需求下的第几批）。`sessionBindingsPending` 表示这些任务仍等待宿主创建执行会话，不代表插件能够自行生成会话。不要声称写入成功，除非工具返回成功。

## 7. 调整已有任务

用户明确要求调整已建任务时，先执行 `"$TASKBOARD" get-task-board-context` 获取项目内现有任务和依赖；确认任务键后再执行写入。不要把任务标题、描述或依赖变更伪装成重新创建任务。

- 更新任务的标题、描述、收益标签、阶段、模块、所属需求、类型、截止日、备注或排序，执行 `"$TASKBOARD" update-task-board-task`。该动作只改变规划属性，不用于改写执行阶段、状态或进度；所属需求变更时会自动将任务负责人同步为该需求的首位负责人。
- 整体调整某任务的直接前置任务，执行 `"$TASKBOARD" update-task-board-task-dependencies`，传入**完整**的 `depends_on_item_keys` 列表；它会替换该任务的全部直接依赖。依赖可引用当前项目中已有的 `item_key`，服务端会拒绝跨项目任务、自身依赖和成环依赖。
- 只删除其中一条或多条直接依赖，执行 `"$TASKBOARD" delete-task-board-task-dependencies`，传入后置任务的 `item_key` 和要删除的 `predecessor_item_keys`。它会保留其余依赖及连线锚点；不把“删除依赖”理解成删除前置任务本身。
- 三个调整工具会先读取任务当前版本后再写入。并发修改导致版本冲突时，如实报告并重新读取上下文，不得用旧数据覆盖他人的变更。
- 任务面板预览态不允许这些写操作；用户必须先在面板中确认写入。普通对话工作流中，用户明确要求调整即为授权。
