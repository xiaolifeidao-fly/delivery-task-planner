# 需求分析

需求窗口里排在「需求拆解」之前的一步。拆解回答的是「这条需求要拆成哪些任务」，
本技能回答的是更前面的问题：**这条需求到底要做什么、在现有工程里落在哪、边界在哪、验收算什么**。
产出的需求分析文档随后可以在需求拆解会话里用 `@` 引用，作为拆解的输入。

| 技能 | 负责 |
| --- | --- |
| **`delivery-requirement-analysis`** | **本技能：把一条需求分析清楚，产出需求分析文档（可含原型）** |
| `delivery-task-planner` | 把需求拆成任务并写入面板 |
| `delivery-requirement-grooming` | 把一条任务梳理成需求文档 |
| `delivery-action-execution` | 按文档实现并交付产物 |
| `delivery-testing-report` | 验收产物并产出测试报告 |

## 会话前提

- 这一轮由需求窗口的执行桥发起，需求已经落库，`requirementKey` 和项目工作目录都写在提示词里。
- 本轮 cwd 就是项目管理里为这个项目绑定的代码仓库；所有结论都要落在这个目录里的真实文件上。
- 不要创建、领取或推进任何任务，不要调用任务状态流转工具，不要改业务代码、配置或依赖。
- 不要提交、推送或切换分支。

## 1. 先进工作目录，再加载项目技能

动手前先加载这个工作目录里项目自己的开发技能（如 `backend-development`、`web-development`）。

**技能不一定在工作目录根上。** 单仓多工程的项目里，前端、服务端、移动端各自的根目录都可能带一份自己的技能：

- 根目录：`.claude/skills/`、`.codex/skills/`
- 子工程根目录：例如 `client/web/`、`client/app/`、`server/` 各自的 `.claude/skills/`、`.codex/skills/`

做法固定为：先按这条需求涉及的端和模块定位到对应子工程，再把**那个子工程的技能连同根目录的一起加载**；
一条需求同时动前端和服务端时，两边的技能都要加载。两处都没有才算没有，不要拿通用最佳实践顶替项目自己的约定。

## 2. 核实工程事实，不要凭空写

需求分析的价值在于「基于当前代码的事实」，而不是把用户的一段话换个说法复述一遍。落笔前先查：

- 需求涉及的目录、现有实现、命名与分层约定。
- 已有接口、表结构、配置项的真实形态，用文件路径作为依据。
- 与本需求冲突、重复或已经做过一半的既有实现。

查不准的地方一律标成「待确认」，不要编造文件名、字段名或接口路径。

## 3. 引导补全，先问后写

默认每一轮都是**澄清回合**：只在聊天里对话，不写任何文件。

- 每轮最多问三到五条，按「不问清就没法动手」的程度排序；能自己从代码里查到的不要问用户。
- 回复固定分三段：
  1. **本轮已确认的事实**（附文件路径依据）；
  2. **还需要用户确认的问题清单**（编号，便于用户逐条答复）；
  3. **需求分析初步框架**（提纲即可，不展开成正文）。
- 常见需要问清的方面：使用者与场景、触发入口、核心流程与分支、数据来源与口径、权限与可见性、
  与既有功能的关系、异常与边界、非功能要求（性能、兼容、迁移）、验收怎么算通过。
- 信息足够时，明确告诉用户「可以点确认生成需求分析文档了」，**但不要自己去写文件**。
  写文档只发生在用户点了「确认生成需求分析文档」的那一轮，提示词里会写明这一点。

## 4. 产出需求分析文档

确认生成的那一轮，把已经在会话里确认下来的口径整理成正式文档，写入 `doc/analysis/<需求键>/需求分析.md`。

该目录支持多份文档：`需求分析.md` 是主文档；接口清单、数据字典、流程说明等要独立成文时，
用独立文件名并列放在同一目录，不要覆盖主文档。

建议结构：

1. **摘要**：三到五行说清目标、范围边界和验收口径，能独立读懂。
2. **需求背景与目标**：为什么做，做完之后什么变了。
3. **当前工程事实**：表格列「项目 / 结论 / 依据」，依据必须是仓库里的真实路径。
4. **范围与不做的事**：明确边界，避免后续拆解扩散。
5. **功能点与业务规则**：按流程或模块列，规则能定死的就定死。
6. **数据与接口影响**：涉及的表、字段、接口、配置，标明新增还是改造。
7. **依赖与风险**：外部依赖、迁移成本、兼容性问题。
8. **验收口径**：怎么算做完，可验证。
9. **开放问题**：仍待用户确认的条目，逐条列出，不要藏在正文里。

重复生成时**按章节定点编辑**：定位到要改的章节写进去，需要新增内容时追加新章节，其余章节一个字都不要动。
不要整篇重写，更不要用只含本轮增量的内容覆盖整份文件。

最终回复第一行必须是「需求分析文档已生成」，随后列出本轮写入的相对路径和改动摘要。

## 5. 需要原型时

用户在面板上开了原型开关，或在聊天里明确要求画原型时，才产出 HTML 原型。

- 原型只能写进 `doc/requirements/<需求键>/prototype/`，遵循本插件的 `requirement-prototype` 技能。
- 按功能模块拆成多个可独立在浏览器打开的 UTF-8 `.html` 页面，至少提供一个 `index.html` 入口，
  使用内联 CSS/JS 或同目录本地资源，不引用远程资源。
- 原型是需求分析的佐证，不是业务实现：不得修改业务代码、配置或依赖。

## 完成检查

- 澄清回合：确认自己没有写任何文件，问题清单编号清晰、可逐条答复。
- 生成回合：确认 `doc/analysis/<需求键>/` 下的文档确实落盘，章节完整，「待确认」项没有被伪装成结论。
- 最终回复列出的都是工作区相对路径，方便面板登记和预览，也方便用户在需求拆解会话里 `@` 引用。
