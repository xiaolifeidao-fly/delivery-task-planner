# 需求级执行验收模式

什么时候读：桥接提示词写明本轮是**执行验收模式**时。用例设计模式不看本文件。

开始前先读 `doc/test/<需求键>/测试用例.md`，按已有用例真实验证。

## 1. 整体测试准备

1. 将需求目标和用户在聊天中追加的要求拆为可验收条目：**前置/输入、操作、预期、观测证据**。
2. 按关联任务的依赖、代码调用方向和业务流程建立测试对象与执行顺序。需要时读取关联任务的 `文档.md`、动作执行产物和任务级测试报告，不能只凭任务标题猜测。
3. 建立并落盘测试准备清单：环境地址、测试账号/角色、鉴权来源、测试数据、外部依赖、素材、清理方式。缺少关键条件时说明最小补充项，不得虚构 Token 或账号。
4. 在 `测试计划.md` 记录每个用例的关联任务、输入、步骤、预期和证据位置；跨任务主路径应从上游准备动作开始，到最终业务结果或交付物结束。

## 2. 执行与证据

- **接口/服务**：按真实顺序验证鉴权、前置实体、触发动作、查询/消费结果、关键副作用和清理；保留脱敏请求摘要、状态码和关键字段。
- **UI**：准备可用账号和初始状态后，用项目既有自动化或浏览器操作覆盖关键路径、权限和错误提示；保存截图或可复查页面证据。
- **脚本、数据和媒体交付**：使用版本化输入和隔离输出，核对日志、文件、数据库记录、时长、格式、字幕、画面/版式等对应验收项。
- 优先使用测试环境、夹具和可回滚数据；不把生产环境当作默认测试环境。

## 3. 总体验收

每条需求级验收标准和关键跨任务用例都标为：**通过 / 不通过 / 未覆盖**，附实际结果和证据。

- **通过**：全部必要项已实际执行，结果与预期一致。
- **不通过**：已执行但结果不符；写清复现、期望/实际、影响和应回到哪个任务/代码位置修复。
- **未覆盖**：缺少环境、账号、数据、外部依赖或口径；写清缺什么、补齐后如何重测。

总体结论规则：必要项全通过为“通过”；任一必要项不通过为“不通过”；没有不通过但有关键未覆盖为“受阻”。

## 4. 结束本轮

先读取 `doc/test/<需求键>/测试用例.md`，完成真实验证后更新 `doc/test/<需求键>/测试报告.md`，再以相同结论回复。最终回复第一行必须且只能是：

```text
验收判定：通过
验收判定：不通过
验收判定：受阻
```

报告至少包括：

1. 测试范围、关联任务和执行顺序。
2. 测试准备：环境、账号/角色、数据、依赖与清理（全部脱敏）。
3. 测试用例：关联任务、输入/前置、操作、预期、实际、证据。
4. 需求验收标准逐条结论。
5. 缺陷、受阻项和应回流的任务。
6. 遗留风险及 `doc/test/<需求键>/` 中资产链接。

没有明确输入、实际执行和可复查证据，不得写“通过”。
