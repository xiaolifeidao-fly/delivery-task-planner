# 需求测试用例与总体测试

这是**需求维度**的测试工作：先可与研发并行设计用例，再验证多个关联任务是否共同满足一条需求的业务目标、跨任务接口和端到端路径。不要把它当成某个任务的成品测试，也不要重新执行无关任务的全量回归。

## 选择本轮模式

桥接提示词会指定模式，必须严格遵守。

| 模式 | 工作边界 | 产物 |
| --- | --- | --- |
| **测试用例设计模式** | 读取需求、关联任务、代码和已有产物，设计关联任务、跨任务顺序、测试数据、环境、账号/Token 来源、步骤、预期和证据；**不得执行**接口、UI、脚本或构建，也不得写验收判定/报告 | `doc/test/<需求键>/测试用例.md`，按需 `测试计划.md` |
| **执行验收模式** | 先读已有用例，再真实准备、执行、取证、对比和判定 | `doc/test/<需求键>/测试报告.md` 及脚本、夹具、证据 |

### 测试用例设计模式

1. 按需求目标、验收标准、关联任务依赖、代码调用方向和业务流程建立跨任务测试范围与顺序。任务仍在研发的地方写为执行前置，不得猜造实现或结果。
2. 形成用例表：**编号 / 关联任务与验收项 / 对象类型 / 前置和脱敏数据 / 操作顺序 / 预期 / 证据要求 / 缺口**。覆盖接口（鉴权、依赖实体、请求形状与关键断言）、UI（账号角色、页面路径、初始状态）、脚本/数据/媒体（输入、输出、核验指标）和端到端链路。
3. 记录环境地址、账号角色、Token 来源类型、测试数据、外部依赖、素材、清理方式和缺失项。不得写凭据原文、Cookie、私钥或生产数据。
4. 写入 `doc/test/<需求键>/测试用例.md`，按需写 `测试计划.md`。不要创建或覆盖 `测试报告.md`，也不要写任何验收判定。
5. 最终回复第一行必须且只能为 `测试用例已生成`，并说明覆盖范围、执行顺序和最小待补条件。

以下执行章节仅适用于**执行验收模式**。

## 固定边界与产物

- 提示词会给出需求详情、所属项目、关联任务清单和每项任务的文档/产物路径；先读这些事实，再从代码、路由、调用链和交付物确定整体测试范围。
- 本轮只做总体测试和报告，不修改业务实现；发现缺陷要精确定位回对应任务或代码位置。
- 所有本轮测试资产必须放在项目工作目录的 `doc/test/<需求键>/`，其中 `<需求键>` 使用面板给出的 `requirementKey`。
- 设计模式至少写入 `测试用例.md`；执行模式写入 `测试计划.md` 和 `测试报告.md`。测试脚本放 `scripts/`、脱敏夹具放 `fixtures/`、截图/日志/样本放 `evidence/`。不要创建空目录，不要写入密码、Token、Cookie、私钥或生产个人数据。
- 需求总体报告会同步到需求右侧的“测试报告”视图；任务级报告仍只挂在各自任务上，两者不可互相覆盖。

## 1. 整体测试准备（执行验收模式）

1. 将需求目标和用户在聊天中追加的要求拆为可验收条目：**前置/输入、操作、预期、观测证据**。
2. 按关联任务的依赖、代码调用方向和业务流程建立测试对象与执行顺序。需要时读取关联任务的 `文档.md`、动作执行产物和任务级测试报告，不能只凭任务标题猜测。
3. 建立并落盘测试准备清单：环境地址、测试账号/角色、鉴权来源、测试数据、外部依赖、素材、清理方式。缺少关键条件时说明最小补充项，不得虚构 Token 或账号。
4. 在 `测试计划.md` 记录每个用例的关联任务、输入、步骤、预期和证据位置；跨任务主路径应从上游准备动作开始，到最终业务结果或交付物结束。

## 2. 执行与证据（执行验收模式）

- **接口/服务**：按真实顺序验证鉴权、前置实体、触发动作、查询/消费结果、关键副作用和清理；保留脱敏请求摘要、状态码和关键字段。
- **UI**：准备可用账号和初始状态后，用项目既有自动化或浏览器操作覆盖关键路径、权限和错误提示；保存截图或可复查页面证据。
- **脚本、数据和媒体交付**：使用版本化输入和隔离输出，核对日志、文件、数据库记录、时长、格式、字幕、画面/版式等对应验收项。
- 优先使用测试环境、夹具和可回滚数据；不把生产环境当作默认测试环境。

## 3. 总体验收（执行验收模式）

每条需求级验收标准和关键跨任务用例都标为：**通过 / 不通过 / 未覆盖**，附实际结果和证据。

- **通过**：全部必要项已实际执行，结果与预期一致。
- **不通过**：已执行但结果不符；写清复现、期望/实际、影响和应回到哪个任务/代码位置修复。
- **未覆盖**：缺少环境、账号、数据、外部依赖或口径；写清缺什么、补齐后如何重测。

总体结论规则：必要项全通过为“通过”；任一必要项不通过为“不通过”；没有不通过但有关键未覆盖为“受阻”。

## 4. 结束本轮（执行验收模式）

先读取 `doc/test/<需求键>/测试用例.md`，完成真实验证后更新 `doc/test/<需求键>/测试报告.md`，再以相同结论回复。最终回复第一行必须且只能是：

```text
验收判定：通过
验收判定：不通过
验收判定：受阻
```

报告至少包括：

1. 测试范围、关联任务和执行顺序。
2. 测试准备：环境、账号/角色、数据、依赖与清理（全部脱敏）。
3. 测试用例：关联任务、输入/前置、操作、预期、实际、证据。
4. 需求验收标准逐条结论。
5. 缺陷、受阻项和应回流的任务。
6. 遗留风险及 `doc/test/<需求键>/` 中资产链接。

没有明确输入、实际执行和可复查证据，不得写“通过”。
